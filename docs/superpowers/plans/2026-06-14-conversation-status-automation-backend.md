# Conversation Status Automation + Setting (Backend) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Automate conversation status by message flow ("whose turn is it") on the server, gated by a per-store, Owner-configurable parameter that auto-reopens resolved conversations when the customer writes back.

**Architecture:** A pure, runtime-agnostic engine (`src/providers/whatsapp/statusFlow.ts`) decides the next status. The inbound webhook core and the outbound send core call it and persist the change through new injected DB methods; the two Edge adapters (`whatsapp-webhook/index.ts` and `_shared/whatsappSendAdapter.ts`) implement those methods. The setting lives as a new key in the existing `stores.settings` jsonb blob (no migration), defaulting to `true` when absent, edited from a new Owner-only Configurações page and read server-side by the webhook adapter.

**Tech Stack:** TypeScript (strict), Deno (Supabase Edge Functions), Vitest (pure logic), React 19 + shadcn/ui, TanStack Router (file-based), bun, Supabase CLI.

**Prerequisite:** This plan assumes Plan A (`2026-06-14-conversation-status-control-frontend.md`) is merged, since it relies on the `em_andamento`/`aguardando`/`aguardando_cliente` semantics being surfaced. It does NOT require Plan A to compile, but ship A first.

```ts
/**
 * Conversation status transitions ("whose turn is it") — pure & runtime-agnostic
 * (no imports, Web-API-free) so it mirrors into the Edge tree and is unit-tested.
 * Consumed by the inbound webhook core and the outbound send core.
 */
export type ConversationStatusValue =
  | "aguardando"
  | "em_andamento"
  | "aguardando_cliente"
  | "resolvida"
  | "arquivada";

/**
 * Next status when the CUSTOMER sends an inbound message.
 * - resolvida → aguardando only if the store enabled auto-reopen.
 * - arquivada → never auto-touched (separate axis, manual).
 * - while the SDR is driving, do NOT push to the human queue (returns null),
 *   except a resolved conversation, which reopens regardless.
 * - em_andamento / aguardando_cliente → aguardando ("the ball is back with us").
 * - aguardando → null (no-op).
 */
export function nextStatusOnInbound(
  current: string,
  opts: { isSdrActive: boolean; autoReopenResolved: boolean },
): ConversationStatusValue | null {
  if (current === "resolvida") return opts.autoReopenResolved ? "aguardando" : null;
  if (current === "arquivada") return null;
  if (opts.isSdrActive) return null;
  if (current === "em_andamento" || current === "aguardando_cliente") return "aguardando";
  return null;
}

/** Next status when a HUMAN sends an outbound message: claim a waiting conversation. */
export function nextStatusOnOutboundHuman(current: string): ConversationStatusValue | null {
  return current === "aguardando" ? "em_andamento" : null;
}
```

```tsx
export function ConversationAutoReopenSettingsPage() {

  const { currentStoreId } = useCurrentStore();

  const { settings, loading, saving, update } = usePlatformSettings(storeId);

              “Aguardando”. Desligado, a conversa permanece resolvida.

          </div>
          <Switch id="auto-reopen" checked={enabled} onCheckedChange={setEnabled} />
        </div>
        <div className="mt-4 flex justify-end border-t border-border pt-4">
          <Button onClick={handleSave} disabled={!dirty || saving}>
            {saving ? "Salvando…" : "Salvar"}
          </Button>
        </div>
```
